## NOSQLI-001

**Severity:** Critical  
**File:** `SeNest/src/courses/courses.service.ts`, lines 25–37

### Vulnerable Code

```typescript
async getAllCourses(queryString: queryStringDto): Promise<…> {
    const queryObj = {...queryString};         // (1) copy all query params
    if(queryObj.search) delete queryObj.search;

    let queryStr = JSON.stringify(queryObj);   // (2) serialize to JSON
    queryStr = queryStr.replace(              // (3) inject $ prefix
        /\b(gte|gt|lte|lt)\b/g,
        (match) => `$${match}`
    );

    const courses = await this.coursesModel.find(
        {...JSON.parse(queryStr), ...searchQuery}  // (4) passed directly to Mongo
    ).populate("instructor").exec();
```

The controller has **no `@UsePipes(ValidationPipe)`** on `getAllCourses`, so NestJS forwards every
query parameter the HTTP client sends — the `queryStringDto` type annotation is advisory only.

Express/`qs` parses bracket-notation query strings into nested objects, so:

```
GET /courses?price[gt]=0&price[ne]=9999
```
arrives as `queryString = { price: { gt: '0', ne: '9999' } }`.  
After the replace step: `{ price: { $gt: '0', ne: '9999' } }` → passed to MongoDB.

Because `ne` (and any other MongoDB operator) is not in the regex allowlist it is passed
through unchanged, but an attacker can send it **with the `$` already present** using
`%24` URL-encoding:

```
GET /courses?%24where=this.title.length>0
```
arrives as `{ '$where': 'this.title.length>0' }` and lands directly in the Mongoose query.  
If the MongoDB server has `javascriptEnabled` (default on older versions), this executes
server-side JavaScript.

Even without JS execution:

```
GET /courses?search=x&%24comment=exfiltrate
GET /courses?price[%24regex]=.*&price[%24options]=is
```

### Root Cause

1. No global or per-route `ValidationPipe` → DTO type annotations are not enforced.
2. The field-to-operator substitution pipeline (`JSON.stringify → replace → JSON.parse`) treats
   the entire query object as a MongoDB filter template with zero allowlisting.
3. No field-name allowlist on the spread into `coursesModel.find(…)`.

### Fix

```typescript
// courses.service.ts — getAllCourses — safe rewrite
async getAllCourses(queryString: queryStringDto): Promise<…> {
    // Build filter explicitly from known-safe fields only.
    const filter: Record<string, unknown> = {};

    // Numeric range: accept only plain numbers, never objects.
    if (queryString.price !== undefined) {
        const n = Number(queryString.price);
        if (!isNaN(n)) filter['price'] = n;
    }
    if (queryString.language) filter['language'] = String(queryString.language);
    if (queryString.level)    filter['level']    = String(queryString.level);

    const searchRegex = queryString.search
        ? escapeRegex(queryString.search)   // escape before use in $regex
        : '';
    const searchQuery = { title: { $regex: searchRegex, $options: 'i' } };

    const combined = { ...filter, ...searchQuery };
    const courses = await this.coursesModel.find(combined).populate('instructor').exec();
    const count   = await this.coursesModel.countDocuments(combined);
    return { courses, count };
}

// helper — escapes all special regex metacharacters
function escapeRegex(s: string): string {
    return s.replace(/[.*+?^${}()|[\]\\]/g, '\\$&');
}
```

Also add to the controller:

```typescript
// courses.controller.ts
@Get()
@UsePipes(new ValidationPipe({ whitelist: true, forbidNonWhitelisted: true }))
async getAllCourses(@Query() queryString: queryStringDto) { … }
```

And add validators to `queryStringDto`:

```typescript
export class queryStringDto {
    @IsOptional() @IsNumber() @Type(() => Number) price?: number;
    @IsOptional() @IsString() @MaxLength(50)       language?: string;
    @IsOptional() @IsString() @MaxLength(50)       level?: string;
    @IsOptional() @IsString() @MaxLength(200)      search?: string;
}
```

## REDOS-001

**Severity:** High  
**File:** `SeNest/src/courses/courses.service.ts`, line 33

### Vulnerable Code

```typescript
let searchQuery = {
    title: {
        $regex: queryString.search || "",  // ← raw user string, unescaped
        $options: 'i',
    },
}
```

An attacker sends a catastrophic backtracking regex pattern:

```
GET /courses?search=^(a%2B)%2B%24
```

MongoDB evaluates the regex server-side. Patterns like `^(a+)+$`, `^([a-zA-Z]+)*$`, or
`(.*a){20}` can cause exponential evaluation time proportional to the document count,
effectively creating a CPU denial-of-service on the MongoDB server.

### Fix

Use `escapeRegex` (shown in NOSQLI-001 fix) before passing to `$regex`, and enforce `@MaxLength`
on the `search` DTO field.

## AUTH-001

**Severity:** High  
**File:** `SeNest/src/courses/courses.controller.ts`, line 78

### Vulnerable Code

```typescript
@Delete(":id")
@UseGuards(AuthGuard('jwt'))
async deleteCourse(
    @Param("id") id: string,
    @Body() email: string          // ← email comes from request BODY, not JWT
): Promise<void> {
    return this.coursesService.deleteCourse(id, email);
}
```

```typescript
// courses.service.ts
async deleteCourse(id: string, email: string): Promise<void> {
    await this.coursesModel.findByIdAndDelete(id);
    this.userService.deleteCourse(email, id);  // de-links from victim's account
}
```

Any authenticated user can delete **any** course by providing another user's email in the
request body.  The JWT guard only checks that a valid token is present; it does not verify
that the caller owns the course being deleted.

### PoC

```bash
# Attacker is logged in as attacker@example.com
# Victim owns course with _id = 64a0000000000000000000aa

curl -X DELETE http://localhost:3000/courses/64a0000000000000000000aa \
  -H "Authorization: Bearer <attacker_token>" \
  -H "Content-Type: application/json" \
  -d '"victim@example.com"'
```

### Fix

```typescript
// courses.controller.ts
@Delete(":id")
@UseGuards(AuthGuard('jwt'))
async deleteCourse(@Param("id") id: string, @Req() request: any): Promise<void> {
    return this.coursesService.deleteCourse(id, request.user.email);
}
```

## AUTH-002

**Severity:** High  
**Files:** `courses.controller.ts` lines 45, 67

### Vulnerable Code

```typescript
@Post("thumbnail/:id")
@UseGuards(AuthGuard('jwt'))          // only checks valid JWT
@UseInterceptors(FileInterceptor(…))
async uploadedFile(@UploadedFile() file, @Param("id") id: string) {
    await this.coursesService.insertImage(id, file.filename);  // no ownership check
    …
}

@Patch(":id")
@UseGuards(AuthGuard('jwt'))          // only checks valid JWT
async updateCourse(@Param("id") id: string, @Body() courseInfo: Courses) {
    return await this.coursesService.updateCourse(id, courseInfo); // no ownership check
}
```

Any authenticated user can overwrite the thumbnail or update the details of any course,
regardless of who created it.

### Fix

```typescript
// courses.service.ts — add ownership helper
async assertOwner(courseId: string, userId: string): Promise<void> {
    const course = await this.coursesModel.findById(courseId).lean();
    if (!course) throw new NotFoundException('Course not found');
    if (course.instructor.toString() !== userId) {
        throw new ForbiddenException('You do not own this course');
    }
}
```

Call `await this.coursesService.assertOwner(id, request.user.id)` at the top of both
`uploadedFile` and `updateCourse`.

## UPLOAD-001

**Severity:** High  
**Files:** `courses.controller.ts:41`, `user/user.controller.ts:31`

### Vulnerable Code

```typescript
filename(req, file, callback) {
    callback(null, Date.now() + path.extname(file.originalname));
    //                          ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
    //  blindly trusts the client-supplied filename
},
```

The stored file is served directly via:

```typescript
// main.ts
app.use("/images", express.static("Images"));
```

Attack surface:
1. **Stored XSS** — upload `evil.html` → stored as `<timestamp>.html` → `GET /images/<timestamp>.html`
   serves attacker-controlled HTML from your origin.
2. **SVG XSS** — `evil.svg` with `<script>` tag, served with `image/svg+xml`.
3. **Script execution** — if the server has a JS/TS loader watching `Images/`, uploading `.js` could
   be loaded, though this is environment-specific.
4. **Extension forgery** — filename `photo.jpg\0.html` truncates at the null byte on some OS paths,
   though Node.js protects against this in most versions.

There is also **no file size limit**, enabling resource exhaustion.

### Fix

```typescript
import { BadRequestException } from '@nestjs/common';
import * as fileType from 'file-type'; // npm i file-type

const ALLOWED_MIME = new Set(['image/jpeg', 'image/png', 'image/webp', 'image/gif']);
const MAX_SIZE_BYTES = 5 * 1024 * 1024; // 5 MB

FileInterceptor('image', {
  storage: diskStorage({
    destination: './Images',
    filename(req, file, cb) {
      const safeName = randomUUID() + allowedExt(file.mimetype);
      cb(null, safeName);
    },
  }),
  limits: { fileSize: MAX_SIZE_BYTES },
  fileFilter(req, file, cb) {
    if (!ALLOWED_MIME.has(file.mimetype)) {
      return cb(new BadRequestException('Only JPEG/PNG/WebP/GIF allowed'), false);
    }
    cb(null, true);
  },
})

// Additionally validate magic bytes after write:
async function validateMagicBytes(filePath: string): Promise<void> {
    const ft = await fileType.fromFile(filePath);
    if (!ft || !ALLOWED_MIME.has(ft.mime)) {
        fs.unlinkSync(filePath);
        throw new BadRequestException('File content does not match declared type');
    }
}
```

Also set `Content-Disposition: attachment` or a restrictive `Content-Type` on the static file
server so browsers don't execute uploaded content inline.

## NPE-001

**Severity:** Medium (denial of service)  
**File:** `SeNest/src/user/user.service.ts`, line 16

### Vulnerable Code

```typescript
async getUser(email: string): Promise<Users> {
    return await (await this.usersModel.findOne({ email })).populate(…);
    //                                                    ^^^
    // if findOne returns null, .populate() throws TypeError: Cannot read
    // properties of null (reading 'populate')
}
```

`getUser` is called from:
- `AuthService.login` — with attacker-controlled email
- `AuthController.checkJwt` → `getUserDetail` — with JWT-extracted email
- `UserController.getDetail` — with JWT-extracted email

The TypeError propagates as an **unhandled rejection**, which in Node.js crashes the process
unless a top-level handler catches it (NestJS does catch it, but returns a 500 with a stack trace
potentially leaking internal paths).

### PoC

```bash
# Email not in the database
curl -X POST http://localhost:3000/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"nobody@example.com","password":"anything"}'
# → 500 Internal Server Error (TypeError: Cannot read properties of null)
# rather than the expected 404 NotFoundException
```

### Fix

```typescript
async getUser(email: string): Promise<Users> {
    const user = await this.usersModel.findOne({ email });
    if (!user) throw new NotFoundException(`User not found: ${email}`);
    return user.populate(['student', 'courses_enrolled', 'courses_created']);
}
```

Apply the same null-check pattern to every other method that chains `.populate()` directly on
an awaited query result.

## DOS-001

**Severity:** Medium (denial of service)  
**File:** `SeNest/src/courses/courses.service.ts`, line 21

### Vulnerable Code

```typescript
async getCourse(id: string): Promise<returnCourseDto> {
    const course = this.coursesModel.findById(id).populate("instructor");
    // Mongoose throws a CastError synchronously if `id` is not a valid ObjectId.
    // This is not caught → NestJS returns 500.
    …
}
```

`@Get(":id")` has no auth guard, so this is unauthenticated.

### PoC

```bash
curl http://localhost:3000/courses/../../etc/passwd
curl http://localhost:3000/courses/NOT_AN_OBJECT_ID
# → 500 Internal Server Error: Cast to ObjectId failed
```

### Fix

```typescript
import { isValidObjectId } from 'mongoose';

async getCourse(id: string): Promise<returnCourseDto> {
    if (!isValidObjectId(id)) throw new BadRequestException('Invalid course id');
    const course = await this.coursesModel.findById(id).populate('instructor');
    if (!course) throw new NotFoundException('Course not found');
    return course;
}
```

Apply `isValidObjectId` guards in `updateCourse`, `deleteCourse`, and `insertImage` as well.

## CONFIG-001

**Severity:** High  
**Files:** `SeNest/src/config/app.config.ts`, `auth/jwt.strategy.ts`, `auth/auth.controller.ts`

### Vulnerable Code

```typescript
// app.config.ts
export default () => ({
    appSecret: process.env.JWT_SECRET,   // undefined if env var not set
})

// jwt.strategy.ts
secretOrKey: appConfig().appSecret,     // undefined → passport-jwt throws at first request

// auth.controller.ts  (checkJwt endpoint)
jwt.verify(token, this.configService.get<string>('JWT_SECRET'));
// If JWT_SECRET is '' (empty string), jsonwebtoken v9 throws "secretOrPublicKey must have a value"
// If JWT_SECRET is undefined, same error
```

If the app starts without `JWT_SECRET` set:
1. The first `/auth/check` call throws an uncaught error.
2. `passport-jwt` strategy is initialized with `undefined` as `secretOrKey`; every protected
   route throws at first use.
3. Any token signed against `undefined` by a different instance behaves unpredictably.

### Fix

Validate required environment variables at bootstrap time:

```typescript
// main.ts
async function bootstrap() {
    const secret = process.env.JWT_SECRET;
    if (!secret || secret.length < 32) {
        console.error('FATAL: JWT_SECRET must be set and at least 32 characters');
        process.exit(1);
    }
    const app = await NestFactory.create(AppModule, { cors: true });
    app.use('/images', express.static('Images'));
    app.useGlobalPipes(new ValidationPipe({ whitelist: true, forbidNonWhitelisted: true }));
    await app.listen(3000);
}
```

## INFO-001

**Severity:** Medium  
**File:** `SeNest/src/user/user.controller.ts`, line 18

### Vulnerable Code

```typescript
@Get()
async getAllUsers() {
    return await this.usersService.getAllUsers();
    // Returns: { users: [{email, password (hash), salt, courses_enrolled, …}], count }
    // Accessible to any bearer-token holder.
}
```

Any authenticated user can enumerate every account including hashed passwords and salts.
Even bcrypt hashes leak account existence and enable offline brute-force attacks.

### Fix

1. Restrict to an admin role with a `@Roles('admin') @UseGuards(RolesGuard)` guard.
2. Strip `password` and `salt` from all user API responses using a response DTO:

```typescript
export class SafeUserDto {
    @Expose() _id: string;
    @Expose() first_name: string;
    @Expose() last_name: string;
    @Expose() email: string;
    @Expose() profile_picture: string;
    // password, salt intentionally excluded
}
```

## VALID-001

**Severity:** Medium  
**File:** `SeNest/src/user/user.controller.ts`, line 56

### Vulnerable Code

```typescript
@Patch()
// @UsePipes(ValidationPipe)   ← commented out
async updateUser(@Req() req: any, @Body() userInfo: SignupDto): Promise<Users> {
    return await this.usersService.updateUser(req.user.email, userInfo);
}
```

Without `ValidationPipe`, any JSON body is accepted, bypassing `@IsEmail`, `@Length`, and
`@IsNotEmpty` decorators on `SignupDto`.  An attacker can set `email` to an empty string,
overwrite another account's email, or inject MongoDB operators via the `email` field used in
`findOneAndUpdate({ email: original_email }, …)`.

### Fix

Uncomment `@UsePipes(ValidationPipe)` and add `{ whitelist: true }` to strip unknown fields:

```typescript
@Patch()
@UsePipes(new ValidationPipe({ whitelist: true }))
async updateUser(@Req() req: any, @Body() userInfo: UpdateUserDto): Promise<Users> { … }
```

Create a dedicated `UpdateUserDto` (all fields optional) rather than reusing `SignupDto`.

## CRYPTO-001

**Severity:** Low  
**File:** `SeNest/src/auth/auth.service.ts`, lines 20–23

### Vulnerable Code

```typescript
const hashedPwd = await bcrypt.hash(password, user.salt);
if (!(hashedPwd === user.password)) {
    throw new ForbiddenException('Invalid credentials');
}
```

This works because bcrypt extracts the embedded salt from `user.salt` (which is a full bcrypt
hash string like `$2b$10$…`) and re-hashes.  However:

1. The separate `salt` field is redundant — bcrypt embeds the salt in the hash.
2. If `user.salt` is ever `null`, `undefined`, or a non-bcrypt string, `bcrypt.hash` generates a
   **new random salt** and produces a hash that never matches `user.password`, silently breaking
   authentication for that account.
3. Timing: `bcrypt.hash` followed by `===` comparison is susceptible to string-comparison
   timing differences in theory (though bcrypt's own `compare` uses `timingSafeEqual`).

### Fix

```typescript
// auth.service.ts
const isValid = await bcrypt.compare(password, user.password);
if (!isValid) throw new ForbiddenException('Invalid credentials');
```

Remove the `salt` field from `UsersSchema` and `UserService.createUser` — it is unnecessary.
